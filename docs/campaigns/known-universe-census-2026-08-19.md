# Known regex universe census at the 2026-08-19 cutoff

The earlier 77-facility artifact is a provisional planning index. It is not an
exhaustive denominator and must not be used to certify discovery completeness.
The compact machine-readable result of the replacement census is
[`known-universe-census-forecast.json`](../../reports/scale/known-universe-census-forecast.json).
The detailed exhaustion ledger remains external to Git and is bound by five
SHA-256 identities in that report.

This work closes systematic breadth discovery at a declared cutoff; it does
not claim a timeless or literally complete inventory. Every catalog lead has a
disposition and no major unexplained category hole remains, but 3,071 explicit
release, runtime, backend, library, profile, diagnostic, historical, and
wrapper-transparency obligations still require later adjudication. Those
unknowns are visible and non-crediting rather than silently omitted.

## Root and facility taxonomy

A discovery root is an ecosystem from which facilities are sought. It is not
automatically an executable facility. Python, for example, is one root.
CPython, PyPy, Jython, MicroPython, CircuitPython, IronPython, GraalPy,
Pyodide, RustPython, Pyston, and Stackless Python are subordinate runtime
candidates. Cython and Hy are separate roots because they are separately
governed languages. Positive facilities and host surfaces are credited only
after a candidate disposition supports them.

The positive facts produce a bounded material-surface census:

| Bound | Material facilities or surfaces | Interpretation |
| --- | ---: | --- |
| Lower | 543 | One credit per positive ecosystem |
| Expected | 746 | Rounded geometric mean of positive ecosystems and ecosystem/backend pairs |
| Conservative | 1,025 | One credit per distinct positive ecosystem/backend pair |

The conservative surface count happens to equal the language-root count. The
two sets are not equivalent. The equality must never be interpreted as one
regex facility for every language root.

Non-mutually-exclusive positive pair counts include 150 language runtime or
runtime-implementation surfaces, 157 standard-library facilities, 129
third-party language libraries, 11 standalone engines, and 146 bindings or
host surfaces. The non-language positive set includes 51 database, data,
search, or managed-service ecosystems and 90 CLI, server, application,
security, or other product ecosystems. Seventy-two normative-only facts remain
separate from execution credit.

## Systematic discovery method

The census started from broad language catalogs rather than the existing
regex list. Each language root was screened for built-in syntax, standard
libraries, runtime implementations, alternative libraries, external-engine
bindings, compatibility packages, and persistent backend modes. Separate
passes covered standalone engines, databases and data systems, managed
services, CLI tools, servers, editors, security products, applications, and
normative standards.

Research used normative standards; official language, runtime, engine,
library, database, service, and product documentation; upstream repositories;
release histories; package registries; dependency and code indexes;
distribution catalogs; platform catalogs; preservation archives; and academic
literature. Package-ecosystem screening covered PyPI, npm, Maven Central,
NuGet, crates.io, RubyGems, Packagist, Go modules, Swift package sources,
pub.dev, Hex, CRAN, Julia General, Hackage, CPAN, LuaRocks, Clojars, and C/C++
distribution catalogs.

The final adversarial cross-category pass added, among other surfaces, H2
regex functions, Kusto regex operations, Cloud Spanner's RE2 functions, two
different Solr regex backends, Traefik routing regexes, Fluentd's Onigmo
parser, and Graylog pipeline regexes. It also prevented false growth: Hive and
Cassandra were already present, and Redis Search wildcard/fuzzy syntax was not
misclassified as regex. These late findings demonstrate why the earlier index
could not be treated as exhaustive.

## Revised factorized-evidence forecast

The forecast scales the corresponding certified factorized Evidence Pack
canary-policy case from the 77-facility basis. It preserves the richer
diagnostic and performance allowances, qualification corpus, targeted
expansion allowance, and general growth reserve. It does not revert to verbose
row-oriented evidence.

| Case | Logical executions | Physical attempts | Objects / Class A / Class B | Universe forecast retained bytes |
| --- | ---: | ---: | ---: | ---: |
| Lower | 242,584,122 | 242,584,122 | 506,048 | 8,050,807,550 |

| Conservative | 2,000,652,267 | 2,100,684,892 | 4,164,323 | 77,597,999,432 |

The lower case is 50,807,550 bytes above the 8,000,000,000-byte operational
soft stop but remains 1,949,192,450 bytes below the 10,000,000,000-byte hard
cap. The expected case exceeds the hard cap by 17,372,369,951 bytes. The
conservative case exceeds it by 67,597,999,432 bytes.

The completed local million-scale qualification remains unpublished. Its
terminal readiness report projects at most 40,552,303 remote bytes, comprising
2,514 content-addressed objects plus 65 deferred control objects. If a later
authorized publication retains it in addition to the universe forecast, the
combined program footprint becomes 8,091,359,853 lower,
27,412,922,254 expected, and **77,638,551,735 conservative bytes**. Current
cloud requests and retained remote bytes for that local pack remain zero.

Publication therefore fails closed. This census authorizes neither paid
capacity nor scientific-scope reduction. A Program Owner decision is required
before material full-universe publication. The precise contributor model
should be refined as the open release/profile obligations are adjudicated, but
the current expected and conservative violations are too large to treat the
old 6.757 GB estimate as controlling.
